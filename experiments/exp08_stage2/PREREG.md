# 실험 8 — 2단계를 살리면 기준선이 얼마나 움직이는가 (**사전 등록**)

> **이 문서는 자료를 보기 전에 커밋한다.** 물음은 자체 심사 M3 이 이미
> 고정했다 (`notes/self_review.md`, 커밋 `d08b830`, 이 실험보다 먼저).

## 왜 하는가 — 기준선의 정체성 문제다

우리가 쓰는 **ultralytics 8.4.46 은 ByteTrack 2단계가 죽어 있다.**
`byte_tracker.py:341-344` 를 직접 확인했다:

```python
dists = matching.iou_distance(r_tracked_stracks, detections_second)
if self.args.fuse_score:
    dists = matching.fuse_score(dists, detections_second)      # cost = 1 - IoU*s
matches, u_track, _ = matching.linear_assignment(dists, thresh=0.5)
```

2단계 검출은 `track_low_thresh(0.1) <= score < track_high_thresh(0.25)` 이므로
`cost >= 1 - IoU*s >= 1 - 0.25 = 0.75 > 0.5`. **어떤 쌍도 통과할 수 없다.**

상류 PR **#25034** (2026-07-06) 가 같은 부등식으로 지적하고 고쳤다. 참조 구현은
**2단계에서 `fuse_score` 를 걸지 않는다.**

> **그래서 exp00·02·03·05·06 이 전부 "2단계가 비활성인 트래커" 위에서 돌았다.**
> 조건 간 비교는 유효하지만 **우리 기준선을 "ByteTrack" 이라 부를 수 없다.**
> 그리고 2단계가 하는 일은 **저신뢰 검출로 가림 중인 트랙을 잇는 것** —
> 이 연구가 겨냥한 바로 그 구간이다.

## 무엇을 바꾸는가 — **한 줄. 참조 구현과 같게**

2단계에서만 `fuse_score` 를 걸지 않는다. **1단계·3단계는 손대지 않는다.**

`fuse_score=False` 를 전역으로 주는 것과 **다르다** — 그건 1단계까지 바꾸므로
개입이 둘이 되어 교란된다. 우리는 2단계만 고친다.

### 구현 방법과 그 검산

`site-packages` 를 고치지 않는다. `update()` 를 통째로 베끼지도 않는다
(전사 오류 위험). 대신 `matching.fuse_score` 를 **점수 구간으로 단계를 판별하는
래퍼**로 감싼다:

- 1·3단계 검출은 **전부** `score >= 0.25`
- 2단계 검출은 **전부** `score < 0.25`

두 구간이 겹치지 않으므로 판별이 정확하다. **그리고 이것을 가정하지 않고
검사한다** — 한 호출 안에 두 구간이 섞여 들어오면 **예외를 던진다.**
섞인 호출이 한 번이라도 있으면 이 방법은 무효이고, 그때는 판정하지 않는다.

## 사전 등록한 사전 점검

| # | 사전 점검 | 통과 기준 |
|---|---|---|
| **[0a]** | 결함 재현 — 고치기 **전** 2단계 채택 건수 | **정확히 0** 이어야 한다 |
| **[0b]** | 수정 확인 — 고친 **후** 2단계 채택 건수 | **0 보다 커야** 한다 |
| **[0c]** | 단계 판별 — 점수 구간이 섞인 `fuse_score` 호출 | **0 건**이어야 한다 |
| **[0d]** | 재현 — 고치기 전 조건이 기존 기록과 일치 | HOTA **61.002** 와 0.01 이내 |

**[0a] 나 [0c] 가 깨지면 판정하지 않는다.** [0a] 가 깨지면 우리가 exp00 에서
낸 "2단계가 죽었다" 가 틀린 것이고, [0c] 가 깨지면 개입이 2단계에 한정되지
않은 것이다.

## 사전 등록한 평가지표

| # | 평가지표 | 묻는 것 |
|---|---|---|
| **[1]** | HOTA(iou, 2단계 **살림**) − HOTA(iou, 2단계 죽음) | **주 평가지표.** 기준선이 얼마나 움직이는가 |
| [2] | AssA·DetA·IDSW 의 같은 차이 | 움직임이 **연관**에서 오는가 |
| [3] | 2단계 채택 건수 / 시퀀스 | 개입의 크기 |

검출은 **캐시 재생이라 두 조건이 비트 단위로 동일**하다. 바뀌는 것은 2단계 비용
하나뿐이다.

### 읽는 법 — 미리 고정한다

**판정 기준을 여기서는 쓰지 않는다.** 이건 두 구현의 차이를 재는 **기술적 측정**이지
새 장면으로의 일반화가 아니다 (CLAUDE.md 규칙 6). 그래서 n=7 검정력이 걸리지
않는다. 그래도 시퀀스별 값을 전부 적고 가중·비가중을 둘 다 보고한다.

| [1] | 함의 |
|---|---|
| `\|Δ\| < 0.3` | 2단계가 거의 일을 안 한다. **기존 결과의 한계 서술이 가벼워진다** |
| `0.3 ~ 2.0` | 기준선이 움직인다. **한계로 명시하고 주요 대조를 재실행해야 한다** |
| `> 2.0` | **기존 추적 수준 결과를 전부 다시 재야 한다** |

**어느 쪽이 나와도 exp05·exp06 의 조건 간 비교 자체가 무효가 되지는 않는다** —
그것들은 같은 트래커 안의 비교였다. 바뀌는 것은 **"ByteTrack 기준선" 이라는
이름을 쓸 수 있는가**이다.

## 이 실험이 답하지 않는 것

- **다른 조건(와서스타인 등)를 다시 재지 않는다.** [1] 이 크면 그건 별도
  작업이고, 그때는 `C` 보정도 **고친 트래커에서 다시 풀어야** 한다
  (사전 등록한 절차를 바꾸지 않는다 — CLAUDE.md 규칙 2)
- 상류 PR #25034 의 **다른 변경사항은 반영하지 않는다.** 우리는 2단계
  `fuse_score` 한 줄만 참조 구현과 맞춘다
- MOT17 val_half 7시퀀스, 1회 실행
